# Ingest: one request, two clouds, one query

Status: built and run on 2026-11-08. The code is the
[ingest-agent](https://github.com/converged-computing/ingest-agent) library, the sibling
of topology-agent: a deterministic engine (`ingest-agent match`) and a behalf agent
(`ingest-agent run`) over it; this repository holds the sample requests
(`experiments/requests/`) and the `make ingest` targets that call it. Nothing here runs in
the cloud; the query runs against the graph database built by `make graphdb` at the
repository root, 1,899 Google and 5,716 AWS exact offers. Cloud cost: $0.

## Question

The graphs were built to be asked. A request for nodes of a shape (cores, accelerators,
memory, network, storage) should become one question of the folded graphs of every cloud,
and the answer should be the offers that can hold it, ranked, so that a site-level
scheduler (the secretary, holding that site's exact graph in Fluxion) only ever sees
requests that can land. This experiment builds that front door and asks: how often is
the ingest right, what does it cost to ask, and where does the folded view say yes when
the exact graph says no?

## Request

A Flux jobspec (`ingest-agent example` prints one), so the document the ingest matches is
the one the secretary hands to Fluxion. The resources tree names what the graphs have
vertices for: a `node` with its count, and under it (through a `slot`, and sockets if
spelled out) `core`, `gpu`, `memory` in GB, `nic` in Gbps and `local_ssd`; a storage pool
type (`pd_ssd`, `ebs_gp3`, ...) beside the node asks for a pool of at least that many GB.
What the graphs hold as properties rather than vertices sits in
`attributes.system.requires`: `gpu` (the accelerator model prefix), `nic` (the kinds),
`placement`, `providers`, `regions`, `zones`, `models`. Fluxion's own hierarchy above the
node (site, provider, region, zone, offer, placement) may be spelled out or left off.
Samples are in `experiments/requests/`.

## Query

One Cypher statement over the exact-level fold in LadybugDB, generated by
`ingest_agent.query.match_cypher`. Offers carry the request's dimensions as columns (`cores` per node,
`gpus`, `accelerator`, `memory_gb`, `egress_gbps`), so the filter is numeric; NIC kinds,
local disks and storage pools are matched through the containment edges; the nodes an
offer can supply are the fold's placement count times nodes per group, and a compact
request needs one group of that size. The rows come back for both clouds in one result
because both hang off the same site root with the same vertex types.

## Ranking

Offers with a known hourly price (AWS, from `aws/cmd/prices`) first, by the request's
hourly total (Spot at the zone's current price); the rest by fit, the mean share of the
node's cores, GPUs and memory the request would leave idle. A Google price feed is the
missing piece for a fair cross-cloud ranking; until then Google offers rank by fit after
the priced AWS ones. The graph database holds On-Demand offers for both clouds; Spot
offers (and their zone prices) are the other follow-up.

## The experiment

The experiment itself, the request set in words with structured floors, the runner over
the engine and the agent on a chosen backend and model, and the report that judges the
agent against the engine and totals the cost, lives at the repository root in
`experiments/ingest/` (its README has the hypotheses, the install and run steps and
the measured cost: $0.65 for the first Opus 5.5 run through the Claude Agent SDK, most of
it the harness prompt entering the cache; about $0.10 to $0.15 a request after that, and
the same order on Bedrock, which has no harness prompt).

## The agent

`ingest-agent run` wraps the engine in a behalf task. The agent reads the request in
words, proposes the structured form, matches it, inspects candidates and records a
recommendation. Its bounds are in code: every tool is read-only; a structured request
given alongside the text is the floor, and a proposal that asks for less in any dimension
is refused; the number of matches is budgeted. Its job is what the engine cannot do:
read a request, widen it along the axes the user left open when nothing fits, and
explain the choice.

## Next: the secretary

The ingest's top candidate names a provider, region and zone. The secretary for that site
loads the exact graph for the region (the fidelity experiment's `resource-query` sessions
are that machinery) and matches the request's jobspec. Measuring agreement between the
ingest's yes and the secretary's allocation, across both clouds, is the experiment proper;
this document records the ingest half.

## First run

The five sample requests against the On-Demand offers of us-central1 and us-east-1, ranked
by fit (`make ingest-all`), each query answering in about a second:

| Request | Best fit | Also fits |
|---|---|---|
| big-memory: 32 cores, 2 TB, 4 TB of block storage | aws x2iedn.16xlarge, 0% idle, $13.34/h, 2 nodes by quota | aws x2idn.32xlarge and x8i.32xlarge (25%), google-cloud c4-highmem-288 (43%, 64 nodes) |
| cpu-batch: 16 nodes of 32 cores and 128 GB | aws c6a.16xlarge, 0% idle, $39/h for the 16 | five more AWS types at 0%; Google n2-standard-64 at 25% further down |
| gpu-training: 2 nodes of 8 H100, 512 GB, RDMA-class NIC, one placement group | aws p5.48xlarge, $110/h for the two, EFA, cluster group | nothing on Google: a3-highgpu-8g has TCPX and the quota allows one node |
| single-gpu: 1 GPU of any kind, 4 cores, local SSD | aws g4ad.2xlarge, $0.54/h | g4dn, g6, trn1 (a Trainium chip counts as the accelerator), g6e, g7e; no Google type has one GPU with local SSD at 4 cores |
| tight-coupled: 32 nodes of 32 cores in one placement group, 100 Gbps | aws c8gn.8xlarge, 0% idle, $61/h for the 32 | aws c7gn, c6in, c8in; google-cloud c3-highcpu-88 (45% idle, compact group of 64) |

What the run found in the graphs, fixed before the numbers above: the AWS exact fold put
every node in its own placement group because the builder wrote the built node count as
the group's capacity, so no compact request could land on AWS; and the database held two
copies of the Google graph (two source databases), which the query now folds with
DISTINCT and `make graphdb` avoids by loading one. Memory is rounded up to whole GB so
the 512 MB nano types are not 0 GB.

What the ranking cannot yet do: compare price across clouds, since only AWS has a price
feed, and consider Spot, since the database holds On-Demand offers. Both are data
additions, not query changes.
